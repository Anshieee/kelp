M2 Polished MVP — it has to survive a normal week Restarts, health checks, better search, measurements, and a deploy you can repeat. Complete

What this is

Making it hold up in ordinary use: picking up where it left off after a restart, self-checks that say whether it is healthy, better search over your own documents, repeatable quality measurements, and a deploy on the Nebius GPU.

Why it matters

A prototype that only works on a good day is a demonstration, not a product. This milestone is the difference between the two.

In plain words

A GPU is the chip that runs large models quickly; Nebius provides ours as a hosted service, so the assistant itself runs on a small ordinary machine and only sends questions out. An eval is a repeatable test of answer quality, not just whether the code runs. A container image is one sealed copy of the app with everything it needs inside, so a server runs exactly what was tested on a laptop.

Status

Complete. Six pieces are done. KEL-5 Skill contracts — the rulebook for new abilities What a new ability must declare before the assistant may use it. Done

What this is

The set of rules an ability has to follow before the assistant is allowed to use it: what it does, what it takes in, what it gives back, and what it is allowed to touch. Without this, every new ability would mean rewiring the assistant by hand. With it, adding an ability is a small, contained job. It is also how the safety layer knows what a tool intends to do before it does anything.

In plain words

A schema is the shape of the data, written down so a machine can check it. A manifest is the label on the box: what is inside and what it needs.

KEL-6 Kernel loop — the thinking engine Turns your message into an answer, and decides when to use a tool. Done

KEL-7 Approval gate — nothing happens until you say yes A checkpoint before every real action, plus a log of what happened. Done

What this is

The check at the door. Before any action that changes something, this layer looks at what the assistant wants to do and decides: allow it, refuse it, or stop and ask you. Asking creates a one-time request that names exactly what will run and expires after ten minutes. Afterwards every decision and result goes into a log that cannot be edited, with keys and passwords removed.

Why it matters

A private assistant that acts for you is only trustworthy if it cannot act behind your back. This is the piece that makes that true, and both the wallet and the demo depend on it.

In plain words

An audit log is a diary of what happened that can only be added to, never rewritten. Deny by default means if the rules say nothing, the answer is no.

KEL-11 Serve entry — one command to run it, one clean stop Boots in order, refuses a second copy, stops cleanly, and picks up a crashed turn. Done

What this is

The first piece of the polished MVP: turning a set of parts into something you can simply run. One command, make serve, starts the HTTP surface, the streaming chat, and tool execution in one process on one port. It reads its settings first and stops with a named error if one is missing, rather than starting halfway. It creates its folders owner-only, refuses to start if another copy already holds the database, and when told to stop it finishes in-flight turns, closes the database, and exits cleanly. On the next start it settles whatever a crash left behind: a turn that was mid-answer is marked interrupted with its finished steps kept, a tool that was still running is failed with a plain reason, and an approval nobody can answer any more is expired, so a late Approve cannot promise a turn that will never happen.

Why it matters

A prototype that needs several terminals and a hand-kept database is a demonstration, not a product. This is the difference between "it works on my machine" and "start it and it runs", and it is what makes a restart safe: nothing is lost and nothing runs twice.

In plain words

A graceful shutdown is a stop that waits for the work in hand instead of pulling the plug. A lock is a marker that says "this database is mine", so a second copy cannot quietly write over the first. An interrupted turn is one the restart closed out, keeping the steps that already finished.

Status

Done. Merged into main at 33994ab from kel-11 (head 46ba746). Boot is ordered and fails fast: settings are validated one variable at a time, folders are created owner-only, and the server logs the steps it took and the port it bound, with no secret value printed. The settings object cannot print a token or key even by accident, and errors name the failing step. A second process on the same database or port is refused with an explicit message instead of racing. Shutdown takes a stop signal, settles in-flight turns within a fixed window, and exits zero. Boot recovery closes interrupted turns, fails stuck tool steps, and expires unanswered approvals, writing the same audit entries a normal decision would. 19 new tests cover all of it, and the full suite is 510. What KEL-11 does not do yet is the dashboard's Retry and Resume buttons, which stay in M2; the deploy it serves arrived later as KEL-16.

KEL-12 Health checks — is it alive, and can it actually serve? Two small endpoints, one honest answer about each dependency. Done

What this is

Two endpoints that let a person or a supervisor ask how the service is doing. /healthz is the liveness check: the process is up and answering. It makes no dependency calls at all, so it stays fast and stays 200 even while the database or the model provider is having a bad day — restarting a live process because a dependency is slow is exactly the wrong move. /readyz is the readiness check: can this process actually serve? It looks at the database (reachable and writable), the migration version, whether the skill manifests loaded, the data directory, and a bounded probe of the model provider. A cached result keeps a slow upstream from turning every check into a wait. The reply names each check, its status, and its latency, and any required check failing returns 503 with the failing check named.

Why it matters

"It is running" and "it can serve" are different questions, and a supervisor needs both answered separately. Without that split, a service either gets restarted for no reason or keeps taking traffic it cannot handle. It is also the first thing anyone looks at when something feels wrong.

In plain words

A liveness check asks "are you there?" and a readiness check asks "can you do the job right now?" A dependency is something the service needs, like its database or the model provider. A probe is a small, time-limited test of that dependency, and a cache reuses a recent answer instead of asking again every second.

Status

Done. Merged into main at 66228bc from kel-12 (head 2c94e0e). Liveness is public and make no state calls; readiness requires the same authentication as the rest of the API. Every probe is bounded and cached, and the response is an envelope of named checks rather than a bare number. The bodies carry no tokens, absolute paths, or exception text: a token or a path in a health body would be a leak with a friendly name. The review tightened four things before the merge. A provider probe now accepts only a 2xx, so a redirect or an auth rejection reads as degraded rather than healthy. A cached probe is stamped when it answers, so its reported age and its thirty-second reuse window describe the answer, not the moment the scrape started. Production wiring is exercised through the real app builder, so a check that is merely configured but not connected cannot pass unnoticed. And probe selection is by presence, not truthiness, so a falsy callable is still run. 38 new tests cover the endpoints, the failure and recovery paths, the latency budgets, and the "no secrets in the body" rule; the full suite is 548.

KEL-13 Real document search — answers quoted from your own files PDFs and spreadsheets are parsed, ranked, and quoted with page and row citations. Done

What this is

The document path grew up. Before this, asking about a PDF or a spreadsheet returned a saved fixture: useful for a repeatable demo, but not an answer about your file. Now a PDF is read page by page with the page numbers kept, and a CSV is read with its header, its inferred column types, and its record numbers kept. Files are stored under a content hash, so uploading the same bytes twice changes nothing. Long documents are cut into overlapping, token-bounded chunks, each carrying the page, sheet, or row range it came from, and no chunk crosses a document boundary. Retrieval is hybrid: a word-matching score and an embedding score are merged, with a deterministic tie-break, a top-k budget, and a relevance floor so a weak match returns nothing instead of noise. The answer is built from the chunks that won, and each claim is shown with a citation naming the page or row it came from.

Why it matters

An assistant that answers from your documents is only trustworthy if you can check the answer against the source. A citation you can open is the difference between "the model said so" and "here is the page". This is also what makes search good enough to use rather than merely present.

In plain words

Chunking is cutting a long document into pieces small enough to search well. An embedding is a list of numbers that stands for the meaning of a piece of text, so similar meanings sit close together. Hybrid search combines word matching with that meaning-matching. A citation is the label that says which page or row an answer came from, so you can look it up yourself.

Status

Done. Merged into main at 7ad39b7 from kel-13 (head 66ddd70), adding 68 tests to a suite of 616. Parsing is defensive: inline images are skipped whole so their binary payload cannot be mistaken for text and fabricate a citation, PDF form fields are followed in place with a depth cap and a cycle guard, a malformed CSV becomes a plain fixable error instead of a raw parser exception, and a very large cell is clipped before it can dominate the index or the answer. The index itself is contained: every write, delete, and load re-checks the resolved path, refuses a symlink where a directory should be, and never deletes anything outside var/index. A single read supplies size, digest, and parse so the file cannot change underneath the check, and a document-wide decompression budget stops a zip bomb even when the bomb is rejected. Retention is deliberately lazy: deleting an artifact does not delete its index on the spot, but the next question prunes the orphaned entry, and an explicit removal hook exists for callers that need an instant guarantee.

KEL-14 Observability — one request id, honest logs, countable metrics A bad turn can be followed from the edge to the tool call without reading anything private. Done

What this is

Three things that make the service observable from the outside. First, one request id per call: a caller may supply X-Request-Id and it is validated, or one is minted, and the same id appears on the response and on every log line the request produces. Second, structured logs: one JSON object per line on stdout, with a fixed allow-list of small fields — request id, thread, turn, tool, status, duration, model, tokens, cost, outcome, error code — and every string scrubbed by the same secret scrubber the audit trail uses. Payload text, prompts, tool arguments, and answers are dropped rather than truncated, so naming a field prompt cannot make it printable. Third, metrics: a dependency-free Prometheus registry served as text at /api/metrics with the same authentication as the rest of the API, covering HTTP requests and latency, turns and their duration, tokens and cost, tool calls by name and status, approval wait, stream resumes, and boot recoveries.

Why it matters

When a turn fails, the question is not "did something go wrong" but "which turn, on which request, in which tool or model call, and how long did it take". Without an id that follows the work and a counter that moves, that answer is a guess. Without a strict field list and a scrubber, the cheapest way to answer it is also the way that copies a customer's document into a log file.

In plain words

A request id is a short label attached to one call so every line about it can be found together. A JSON log line is a log entry written as labelled fields instead of a sentence, so a machine can filter it. Prometheus is a common way to publish numbers a monitoring system can scrape, and a histogram is a set of buckets that shows how long things usually take. A label is a tag on a number; keeping labels short and bounded stops the number of series from exploding.

Status

Done. Merged into main at 38130fb from kel-14 (head 38c3162), adding 31 tests to a suite of 647: 11 for the logging contract, including planted secrets and payload fields that must not appear, and 20 for the metrics registry, the HTTP surface, and the correlation path. The review fixed three behaviour bugs and four smaller ones before the merge. Histograms keep a per-key observation total, so a value above the largest finite bucket still lands in +Inf and in the count instead of vanishing, and a non-finite value is refused rather than poisoning the sum. A model-authored tool name is resolved against the tools actually offered before any sink sees it, so an unknown or crafted name collapses to one fixed bucket and cannot mint a new series or inject a second log line; every label is length-capped. Error codes are threaded into the tool-call log and audit entries and the turn-finished path, shape-checked and kept out of metric labels, and the turn catch-all records only the exception type name. Request ids use a full match, so a trailing newline is rejected and an invalid id is never echoed back. Usage rows from the JSONL and in-memory stores are normalised to one shape, and the usage line says whether the cost and the reported usage are known. JSON is emitted with non-finite numbers refused, and the stock HTTP request logger is silenced so the structured access line is the only record and no unredacted request line reaches stderr.

KEL-15 Eval harness — one command that measures answer quality A repeatable offline check that fails by name when a behaviour the MVP promises breaks. Done

What this is

A versioned set of 26 tasks and a runner that scores them against the real code. make eval blocks outbound sockets at the connect and name-resolution paths, replays recorded model turns, and runs every task three times. The tasks sit in five groups: retrieval, with page N and row N citation locators; tool choice against a recorded model turn; approvals, covering creation, a yes, a no, single use, expiry, and secret redaction; restart recovery, where boot closes out a turn a crash left behind; and multi-turn history, where thread isolation and idempotent client turn ids are checked. Each task declares its own expected result, so adding a case is a data change in evals/datasets/v1/tasks.json, not code. The run scores pass rate, citation precision and recall, tool accuracy, approval correctness, p50 and p95 latency, tokens and estimated cost, and an error rate, then compares the numbers with the gates in evals/thresholds.json. Reports land in var/evals/<timestamp>-<mode>/report.json and report.md.

Why it matters

"The tests pass" only says the code runs. It says nothing about whether a document answer still quotes the right page, whether the model still picks the right tool, whether a write is still refused without a yes, or whether a citation is still real. Those are the promises the prototype makes, and the cheapest way to keep them is a check that names the broken one instead of a number that quietly drifts.

In plain words

An eval is a repeatable test of answer quality, not just of whether the code runs. A recorded fixture is a saved model answer, replayed so the run costs nothing and gives the same result twice. A gate is a number the run has to beat. Deterministic means the same input gives the same output every time, which is what makes a failure mean something.

Status

Done. Merged into main at 793569c from kel-15 (head 225f7c0), adding 22 tests to a suite of 669: 8 for the dataset contract, 6 for the metrics, and 8 for the runner, the gates, and the determinism check. The offline run covers 26 tasks three times each and reports a 100% pass rate, 100% citation precision, 100% tool accuracy, and 100% approval correctness with zero errors, in about 350 milliseconds — far inside the one-minute budget. The network block is a tripwire, not a promise: a task that tries to dial out fails the run instead of passing quietly. Recorded fixtures are labelled recorded://synthetic in every report and hold no credentials and no real documents. Two honest gaps against the written issue. First, the issue names a second target, make eval-live; what shipped is make eval EVAL_ARGS="--live", which is the only path that builds a real provider client, needs NEBIUS_API_KEY, is labelled and non-gating, and still keeps third-party tool output on deterministic stubs. Second, the regression compare reads the most recent offline report for the same dataset version, and those reports live under the gitignored var/, so a clean checkout gates on the thresholds alone while a working tree also catches a drop against the previous run.

KEL-16 Deploy — one image and a runbook that puts it on a server A reproducible container, a startup that never builds or fetches, and steps a stranger can follow end to end. Done

What this is

The deploy slice, with no application code changed. A two-stage Dockerfile resolves the dependencies from pyproject.toml into a venv in the builder and copies only that venv into a python:3.12-slim runtime, which runs as 10001:10001, keeps its root filesystem read-only, drops every capability, and declares /data as its only writable volume. Its HEALTHCHECK is a stdlib probe, deploy/healthcheck.py, that calls /api/healthz or /api/readyz and needs no curl in the image. docker-compose.yml is the supported deployment: it runs a named image and never builds or pulls, requires KELP_IMAGE with no default, publishes on loopback only, and caps the container at 1 GiB and 2 CPUs with log rotation. deploy/kelp.service starts that same project at boot and refuses to start when the tag is unset or its image is missing. The runbook, docs/DEPLOY.md, is seventeen sections from a bare VM to a working turn: build, first deploy, TLS through a reverse proxy, health and readiness, the /data layout, backup and restore, the single-replica rule, rollout and rollback, smoke steps, cost, troubleshooting, a secret checklist, and the verification record.

Why it matters

A deploy is where a tested repository becomes something a person can use, and where every shortcut shows up: a secret baked into a layer, a container running as root, a second writer on the same database, a reboot that leaves the service down, or a startup that quietly builds a different image than the one that was tested. This slice closes those doors on purpose. The image is the unit that was tested, the tag is required rather than defaulted, the tag is checked before anything starts, and the runbook records what was measured instead of what was hoped.

In plain words

A container image is one sealed copy of the app with its libraries inside, so the server runs exactly what was tested. A tag is the image's name and version. Compose is the short file that says how to run it. systemd is the part of Linux that starts things at boot. A reverse proxy is the small server in front that adds HTTPS. A read-only root filesystem means the app cannot rewrite its own code, so an attacker who gets in cannot change it either.

05 / Words

The technical words, in plain English

Everything on this page is meant to be readable without a technical background. If a word still gets in the way, it is probably here.

SDLC
Software development life cycle: the whole trip from an idea to something shipped and looked after. This page is that trip for this product.
KEL number
The name of one work item in Linear, our task tracker. KEL-5 to KEL-16 name the twelve pieces so far: six in the prototype, and KEL-11, KEL-12, KEL-13, KEL-14, KEL-15, and KEL-16 in the polished MVP.
Milestone
A stage of the build, not a feature. M0 is the ground floor, M1 is the first working version, and so on.
Repo and branch
The repository is the project folder kept on GitHub, with its full history. A branch is a separate copy where new work is prepared before it joins the shared copy, called main.
Manifest and schema
A manifest is the label on a tool's box: what it does and what it needs. A schema is the shape of the data, written down so a machine can check it.
Kernel
The thinking loop at the heart of the assistant: read the message, decide, act, answer.
Token
A word-sized chunk of text. Models read and write in chunks, and price is counted per chunk.
Streaming
Sending the answer word by word as it is written, instead of waiting for all of it.
Tool call
The assistant asking a small program to do one specific thing: search the web, read a file, look up an issue.
Approval gate
A checkpoint that stops an action and asks you first. Nothing passes without a yes, and a yes is good for one action only.
Audit log
A diary of what happened that can only be added to. It is how you check the assistant afterwards.
Fixture
A saved sample answer, used so a test or a demo runs the same way every time.
Eval
A repeatable test of how good an answer is, rather than just whether the code runs.
GPU
The chip that runs large models quickly. Nebius provides ours.
Stripe and SetupIntent
Stripe is the payment company that stores card details, so the app never holds them. SetupIntent is Stripe's name for the one-time step that saves a card for later.
Razorpay, hosted Checkout, signature
Razorpay is a second payment company. Hosted Checkout is its own payment page, so the card is typed there, not here. A signature is a short code computed with a shared secret; it proves a message really came from Razorpay and was not altered on the way.
