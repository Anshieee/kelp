KEL-7 Approval gate — nothing happens until you say yes A checkpoint before every real action, plus a log of what happened. Done

What this is

The check at the door. Before any action that changes something, this layer looks at what the assistant wants to do and decides: allow it, refuse it, or stop and ask you. A private assistant that acts for you is only trustworthy if it cannot act behind your back. This is the piece that makes that true, and both the wallet and the demo depend on it.

An audit log is a diary of what happened that can only be added to, never rewritten. Deny by default means if the rules say nothing, the answer is no.

KEL-11 Serve entry — one command to run it, one clean stop Boots in order, refuses a second copy, stops cleanly, and picks up a crashed turn. Done

What this is

The first piece of the polished MVP: turning a set of parts into something you can simply run. One command, make serve, starts the HTTP surface, the streaming chat, and tool execution in one process on one port. It reads its settings first and stops with a named error if one is missing, rather than starting halfway. It creates its folders owner-only, refuses to start if another copy already holds the database, and when told to stop it finishes in-flight turns, closes the database, and exits cleanly. On the next start it settles whatever a crash left behind: a turn that was mid-answer is marked interrupted with its finished steps kept, a tool that was still running is failed with a plain reason, and an approval nobody can answer any more is expired, so a late Approve cannot promise a turn that will never happen.

Why it matters

A prototype that needs several terminals and a hand-kept database is a demonstration, not a product. This is the difference between "it works on my machine" and "start it and it runs", and it is what makes a restart safe: nothing is lost and nothing runs twice.

In plain words

A graceful shutdown is a stop that waits for the work in hand instead of pulling the plug. A lock is a marker that says "this database is mine", so a second copy cannot quietly write over the first. An interrupted turn is one the restart closed out, keeping the steps that already finished.

Status

Done. Merged into main at 33994ab from kel-11 (head 46ba746). Boot is ordered and fails fast: settings are validated one variable at a time, folders are created owner-only, and the server logs the steps it took and the port it bound, with no secret value printed. The settings object cannot print a token or key even by accident, and errors name the failing step. A second process on the same database or port is refused with an explicit message instead of racing. Shutdown takes a stop signal, settles in-flight turns within a fixed window, and exits zero. Boot recovery closes interrupted turns, fails stuck tool steps, and expires unanswered approvals, writing the same audit entries a normal decision would. 19 new tests cover all of it, and the full suite is 510. What KEL-11 does not do yet is the dashboard's Retry and Resume buttons, which stay in M2; the deploy it serves arrived later as KEL-16.

The stream tails nothing new, because the snapshot is immutable, and it closes within one tick of a revoke, expiry, or delete.

The snapshot is a projection, not a copy of the database. Storage paths, content hashes, attachment handles and URLs, approval ids, turn and call ids, and tool-call arguments and results are dropped structurally; pending approval cards are excluded and counted, so a half-finished turn cannot leak an argv payload. The projection is also scrubbed for handle-shaped strings, because a handle can be typed into message text or a citation where no allow-list reaches. A thread larger than 4 MiB is refused rather than truncated.

Why it matters

Sharing is the one feature that could quietly turn a private assistant into a publishing system. Building the smallest version the decision allowed — a capability link with no identity, no write, no model call, and no artifact bytes — gets the useful half of sharing without a second principal, a second credential family, or a data-ownership migration that would have to happen while the database holds someone's conversations.

In plain words

A frozen snapshot is a photograph of the thread taken when the link is made: it does not grow when the conversation continues, so a link can never show something written after it was handed out. Stored as a hash means the server keeps a fingerprint, not the key, so a stolen database does not yield working links. Revoke means the next request is a plain not-found, and an open stream closes within a moment.

How it is kept safe

One lookup, one 404: unknown, empty, malformed, expired, revoked, and purged tokens are hashed and looked up by the same key and rendered by the same builder, so the bodies are byte-identical and no header distinguishes them. The surface is GET only: every other verb under the prefix is a 405 that names GET, the request body is never read, and no content, preview, download, or approval route exists there. The token is never logged, labelled in a metric, or written to an audit row — only its hash is. Both share rate classes fail closed on a limiter fault, and a read is charged per token hash and against a process-wide ceiling before the lookup, so many distinct links cannot collectively exhaust the process. Open anonymous streams are capped process-wide and a refused open is not counted as a view. Every response, including errors, carries no-store, no-referrer, noindex, nosniff, and a deny-everything content policy; a share never sets a cookie, even for an owner. Deleting a thread deletes its links and view counts in the same transaction, expired and revoked rows are swept at boot and daily, and a create re-checks the parent inside its write transaction so a link cannot outlive its thread.

Sharing

One owner, and a read-only link per thread

Decided in writing before any share code exists.

Now
One principal. The owner signs in; there is no workspace, no membership, no invitation, and no second kind of account.
Next
A capability link. Sharing one thread means handing out a revocable, read-only URL that shows a frozen snapshot of that thread and nothing else. Specified as KEL-28, not built.
Rule
A share can never write, ask, or spend. No reply, no edit, no download, no model call, no tool call, and no second person approving a payment.
Rejected
Workspace membership and multi-tenancy. Both would move every table, every credential, and every budget at once. Revisit only when someone concretely needs a second person writing in the same thread.

05 / Words

The technical words, in plain English

Everything on this page is meant to be readable without a technical background. If a word still gets in the way, it is probably here.

SDLC
Software development life cycle: the whole trip from an idea to something shipped and looked after. This page is that trip for this product.
KEL number
The name of one work item in Linear, our task tracker. KEL-5 to KEL-28 name the twenty-four pieces so far: six in the prototype, six in the polished MVP, six in the hardening stage, and six in the longer vision. KEL-19, owner sign-in, and KEL-22, the privacy review, closed the hardening stage; KEL-24, device sessions, opened M4, and KEL-23, KEL-25, KEL-26, KEL-27, and KEL-28 followed with scheduled work, plugins, the written sharing decision, proactive turns, and the read-only share link, which completed it.
Milestone
A stage of the build, not a feature. M0 is the ground floor, M1 is the first working version, and so on.
Repo and branch
The repository is the project folder kept on GitHub, with its full history. A branch is a separate copy where new work is prepared before it joins the shared copy, called main.
Manifest and schema
A manifest is the label on a tool's box: what it does and what it needs. A schema is the shape of the data, written down so a machine can check it.
Kernel
The thinking loop at the heart of the assistant: read the message, decide, act, answer.
Token
A word-sized chunk of text. Models read and write in chunks, and price is counted per chunk.
Streaming
Sending the answer word by word as it is written, instead of waiting for all of it.
Tool call
The assistant asking a small program to do one specific thing: search the web, read a file, look up an issue.
Approval gate
A checkpoint that stops an action and asks you first. Nothing passes without a yes, and a yes is good for one action only.
Audit log
A diary of what happened that can only be added to. It is how you check the assistant afterwards.
Fixture
A saved sample answer, used so a test or a demo runs the same way every time.
Eval
A repeatable test of how good an answer is, rather than just whether the code runs.
GPU
The chip that runs large models quickly. A hosted provider runs ours.
Cron
The old five-column way of saying when something should happen: minute, hour, day of the month, month, and day of the week. A timezone is applied so a wall-clock time fires at the right instant.
Plugin
An ability written by someone else that is installed without rebuilding the assistant. Its package is fingerprinted in a lock file so a changed byte stops the boot.
Digest and pin
A digest is a fingerprint of a set of bytes: change one byte and the fingerprint changes. A pin is that fingerprint written down, so the next boot can tell whether the code is still the code that was installed.
Capability link
A web address that is itself the permission. Whoever holds it can read the one thing it points at, and nothing else, until it is revoked or expires. It is not an account.
Stripe and SetupIntent
Stripe is the payment company that stores card details, so the app never holds them. SetupIntent is Stripe's name for the one-time step that saves a card for later.
Razorpay, hosted Checkout, signature
Razorpay is a second payment company. Hosted Checkout is its own payment page, so the card is typed there, not here. A signature is a short code computed with a shared secret; it proves a message really came from Razorpay and was not altered on the way.
