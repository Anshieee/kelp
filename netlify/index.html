02 / Milestones

Where the build stands

A milestone is a stage, not a feature. Each one is cumulative, so M2 includes everything in M1. All five currently point at the same date; treat that as the target, not a promise.

M0 Foundation — the ground floor Repo, written decisions, tests, and the safety basics. In progress

What this is

The starting shape of the project: the folder kept on GitHub, the written decisions, the test setup, and the choice of model and hosting. Nothing you would look at as a user yet.

Why it matters

Everything after this stands on it. Getting the shape right while the project is small is much cheaper than moving walls later.

In plain words

A threat model is a short list of what could go wrong and what we do about each one. CI is a robot that runs the checks every time code changes.

Status

In progress. The repository (public since this snapshot), the documentation, the tests, and the skill contract are in. Still open: the automated checks, the standard development setup, and the written threat model.

M1 Prototype — the first version you can watch Ask, read a file, approve an action, pay, and see the demo run. In progress

What this is

The end-to-end story. You ask a question, the assistant answers with sources, reads your documents, asks before it does anything that matters, and can pay with a saved card. All six work items, KEL-5 to KEL-10, live inside this milestone.

Why it matters

A plan is not a product. This is the stage where the idea becomes something you can sit in front of and judge for yourself.

In plain words

A branch is a separate copy of the code where new work is prepared before it joins the shared copy. Merged means that work has joined the shared copy for good.

Status

In progress. KEL-5 to KEL-9 are done, merged, and reviewed; the full suite is 491 tests, all passing, and make demo plays all six scenes. KEL-10, payments, has two merged paths: saved cards with caps, approvals, and receipts, and hosted Checkout with order, signature, settlement, and webhook. Both run offline against fake transports. One live test-mode payment still has to be made in a browser, so the item stays in progress.

03 / The work

Six pieces of work, KEL-5 to KEL-10

Each line opens to the same five things: what it is, why it matters, the plain words, where it stands, and the file to read. Open one at a time, or open them all.

KEL-5 Skill contracts — the rulebook for new abilities What a new ability must declare before the assistant may use it. Done

What this is

The set of rules an ability has to follow before the assistant is allowed to use it: what it does, what it takes in, what it gives back, and what it is allowed to touch. Four starter abilities are already built on top of it: web search, reading GitHub, answering from your PDFs and spreadsheets, and creating a scheduled job.

Why it matters

Without this, every new ability would mean rewiring the assistant by hand. With it, adding an ability is a small, contained job. It is also how the safety layer knows what a tool intends to do before it does anything.

In plain words

A schema is the shape of the data, written down so a machine can check it. A manifest is the label on the box: what is inside and what it needs.

Status

Done. Merged into main in b8de92f, with 60 tests covering the contract and loader.

KEL-6 Kernel loop — the thinking engine Turns your message into an answer, and decides when to use a tool. Done

What this is

The part that reads your message, asks the model what to do, sends the answer to you while it is still being written, and — when a tool is needed — runs it, feeds the result back, and keeps going until there is a real answer. It also sets a ceiling on steps and length per turn, and keeps a running tally of the cost.

Why it matters

It is the engine of the product. The chat screen, the approval step, the wallet, and the demo all plug into this loop.

In plain words

Streaming means showing words as they arrive instead of waiting for the whole answer. A tool call is the assistant asking a small program to do one specific thing, like search the web.

Status

Done. Built on kel-6, merged into main at d3c763e; the branch head was 4c72afc. The kernel suite is 43 tests and they pass, alongside the rest of the 491. The code review written up in docs/REVIEW_KEL6_KEL7.md signed off, and KEL-8 built on top.

KEL-7 Approval gate — nothing happens until you say yes A checkpoint before every real action, plus a log of what happened. Done

What this is

The check at the door. Before any action that changes something, this layer looks at what the assistant wants to do and decides: allow it, refuse it, or stop and ask you. Asking creates a one-time request that names exactly what will run and expires after ten minutes. Afterwards every decision and result goes into a log that cannot be edited, with keys and passwords removed.

Why it matters

A private assistant that acts for you is only trustworthy if it cannot act behind your back. This is the piece that makes that true, and both the wallet and the demo depend on it.

In plain words

An audit log is a diary of what happened that can only be added to, never rewritten. Deny by default means if the rules say nothing, the answer is no.

Status

Done. Built on kel-7, merged into main at daf3b14; the branch head was ef6ea9f. The policy check, one-time approvals, gated execution, the audit log, and 50 tests are all in and passing. The review signed off, and KEL-8 built on top.

KEL-8 Dashboard chat — the main screen The conversation where you can see every step the assistant takes. Done

What this is

The place you actually talk to the assistant. Conversations you can name and pick up later, answers that appear as they are written, a small card for each tool step you can open, files you attach to a question, one wider card for a run of GitHub lookups, previews of PDF and spreadsheet answers, labels showing where an answer came from, and approval requests shown right in the conversation.

Why it matters

It is the front door of the product. The demo, the wallet, and every approval happen here, so nothing else can be shown to a person until this exists.

In plain words

A thread is one conversation. An artifact card is a small preview of a file the assistant made for you.

Status

The chat surface is in: named threads you can reopen, an append-only stream of events, a card for each tool step, approvals shown in the conversation over the KEL-7 gate, artifact serving, and a cancel token so Stop works. The chat suite is 86 tests, part of the 491. The spec is on main at docs/CHAT_SPEC.md, 1,164 lines, with its review fixes at 56b0785. The browser screen that draws this surface is still to come.

KEL-9 Demo run — the whole story, played by one command Six short scenes that prove the product works, offline, every time. Done

What this is

Six short scenes, played in order by a single command: ask a question and get sources; summarise a PDF and answer a spreadsheet question; look up a GitHub issue; approve a write and see it in the log; schedule a job; then stop the server mid-answer and pick the conversation back up. Each scene writes a receipt, and the run stops with an error if any scene fails.

Why it matters

It is both the proof and the guard rail. Anyone can watch the product work in a few minutes, and a regression breaks the script before it reaches a person.

In plain words

A fixture is a saved, make-believe answer from the model, used so the run happens the same way every time and works without a network.

Status

Done. Merged into main at 1f08e53; the work was built on kel-9, head 60f653b. make demo plays all six scenes: 129 checks in about two seconds, using the real chat service, answer loop, skill rules, approval gate, and HTTP API, with a recorded model so the run is offline and repeatable. The sixth scene kills a real server process mid-answer and proves the conversation comes back in a new one. The review found that the scheduled scene left its approval unsettled in the log; that is fixed, so every decision ends as executed or denied. Screenshots belong to the dashboard slice; these receipts are the review artefacts.

KEL-10 Payments — saved cards, limits, and hosted Checkout Pay with a saved card or in a hosted Checkout, under a cap, only after you approve it. In progress

What this is

Saving a card once, seeing the cards you have saved, two kinds of limit (per purchase and per month), a small confirmation window before paying, and a receipt afterwards. A second path lets the browser pay in a hosted Checkout instead, where the card is typed on the payment company's page and never reaches this app. Every payment passes through the approval step from KEL-7, so nothing is charged without a yes.

Why it matters

Paying is the clearest example of something the assistant should never do on its own. It shows the safety story with real money at stake.

In plain words

Stripe is the payment company that stores card details, so the app never holds them. SetupIntent is Stripe's name for the one-time step that saves a card for later. Razorpay is a second payment company; a hosted Checkout is its own payment page, and a signature is a code that proves a message really came from Razorpay.

Status

In progress, merged in three steps. The saved-card scaffold came in at 5e270eb from kel-10-scaffold (head a98054b); the Razorpay gateway at 5472c3b from kel-10-razorpay (head cabefb7); the hosted Checkout path at c474c72 from kel-10-checkout (head f07baee). Saved cards, listing, the per-purchase and monthly caps, a confirmation window, approvals, receipts, and Checkout all exist and are covered by 266 new tests: 54 for the wallet, 32 for its HTTP surface, 72 for the Razorpay gateway, 52 for Checkout, and 22 for the Checkout HTTP surface. The full suite is 491. Everything runs offline against fake transports, so no money moves and no key is needed. Keys are read from the server environment only, never leave it, and are redacted from logs, status payloads, and errors. The review of the Checkout path raised four findings and all four are fixed: a saved-card approval and a Checkout order can no longer race for the same order, a paid order with no provider payment id is refused instead of returning someone else's receipt, a provider error no longer fails an order that already has a Checkout registered, and the webhook signature header is mandatory once a webhook secret is set. What is left is one live test-mode payment: someone has to finish a Checkout in a browser, and that confirm or webhook returning a receipt is the proof. Until then the item is not done. An in-app balance stays outside this round. Linear shows KEL-10 as In Progress.

04 / Decisions

What is settled, what waits

Three choices keep the first version small. Anything marked later is deliberately outside this round, not forgotten.

Surfaces

Dashboard first, Telegram second

Where the conversation happens.

Now
Dashboard. The main surface, and the place every flow is designed.
Next
Telegram. A mirror of the same assistant, under the same rules and the same approval step.
Later
WhatsApp. Not in this round. Older notes that call it the main mirror are out of date.
Later
Voice memos. No recording or listening work yet.

Money

Stripe saved cards and Razorpay Checkout now

How paying works, and what is out of scope.

Now
Saved cards with Stripe. Save once, list, a per-purchase cap, a monthly cap, a confirmation window, and a receipt. Tracked by KEL-10.
Now
Hosted Checkout with Razorpay. An order is reserved against the same caps, the browser pays on Razorpay's page, and the return or the webhook is accepted only after a signature and a provider lookup agree on the order, amount, and currency.
Rule
Card details stay with the payment company. The app never stores a card number, so a leak of the app does not leak a card.
Later
In-app balance. Showing a balance, topping it up, and keeping a ledger all wait.

Design

The screen plan is ready

Written and agreed. Not yet drawn.

Done
Thirteen screens covering the conversation, files, sources, GitHub, approvals, scheduled jobs, wallet, memory, activity, and the empty states.
Done
Three flows: drop a file and get a summary; ask for a sweep; propose, approve, then receive.
Done
Four states for every screen: working, waiting on you, failed, done.
Done
The chat spec. Threads, approvals shown in the conversation, artifact cards, and attachments, written out in docs/CHAT_SPEC.md and merged to main with KEL-8 at e0bbb72.
Next
Draw the file, then build the browser screen. The chat surface backend is on main; the screen itself starts once the drawing file exists.

05 / Words

The technical words, in plain English

Everything on this page is meant to be readable without a technical background. If a word still gets in the way, it is probably here.

SDLC
Software development life cycle: the whole trip from an idea to something shipped and looked after. This page is that trip for this product.
KEL number
The name of one work item in Linear, our task tracker. KEL-5 to KEL-10 are the six pieces of the prototype.
Milestone
A stage of the build, not a feature. M0 is the ground floor, M1 is the first working version, and so on.
Repo and branch
The repository is the project folder kept on GitHub, with its full history. A branch is a separate copy where new work is prepared before it joins the shared copy, called main.
Manifest and schema
A manifest is the label on a tool's box: what it does and what it needs. A schema is the shape of the data, written down so a machine can check it.
Kernel
The thinking loop at the heart of the assistant: read the message, decide, act, answer.
Token
A word-sized chunk of text. Models read and write in chunks, and price is counted per chunk.
Streaming
Sending the answer word by word as it is written, instead of waiting for all of it.
Tool call
The assistant asking a small program to do one specific thing: search the web, read a file, look up an issue.
Approval gate
A checkpoint that stops an action and asks you first. Nothing passes without a yes, and a yes is good for one action only.
Audit log
A diary of what happened that can only be added to. It is how you check the assistant afterwards.
Fixture
A saved sample answer, used so a test or a demo runs the same way every time.
Eval
A repeatable test of how good an answer is, rather than just whether the code runs.
GPU
The chip that runs large models quickly. Nebius provides ours.
Stripe and SetupIntent
Stripe is the payment company that stores card details, so the app never holds them. SetupIntent is Stripe's name for the one-time step that saves a card for later.
Razorpay, hosted Checkout, signature
Razorpay is a second payment company. Hosted Checkout is its own payment page, so the card is typed there, not here. A signature is a short code computed with a shared secret; it proves a message really came from Razorpay and was not altered on the way.
